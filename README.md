# 교육사업 CRM

기업·기관을 상대로 교육을 진행하는 회사를 위한 고객 관리 시스템입니다.
고객사 DB, 담당자, 교육 과정과 진행 이력, 영업 파이프라인, 활동 기록을 한곳에서 관리합니다.

## 빠른 시작

```bash
npm install
cp .env.example .env      # DATABASE_URL 확인
npm run setup             # Prisma 클라이언트 생성 + DB 생성 + 데모 데이터 입력
npm run dev               # http://localhost:3000
```

데모 데이터 없이 빈 상태로 시작하려면:

```bash
npm install
cp .env.example .env
npx prisma generate && npx prisma db push
npm run dev
```

| **컨택 아젠다** | `/agenda` | 이번 주 연락할 곳(접촉 주기 도래), 후속 조치, 이번 주 교육 / 월별 시즌 이벤트, 관계 점검 대상 |

| 고객사 상세 | `/organizations/[id]` | **등급·생애주기·기업 프로파일** + 담당자·교육 이력·영업 기회·활동 기록, **담당자 변경 이력** |
| 등급 평가 | `/organizations/[id]/grade` | 5개 축 1~5점 평가 → 가중 평균 → S~D 등급과 접촉 주기 |
| 기업 프로파일 | `/organizations/[id]/profile` | 예산 편성월, 채용·교육 시즌, HR 구조, 조직문화, 확장 가능성 |

| 영업 파이프라인 | `/deals` | 문의 → 제안 → 견적 → 계약 → 완료 / 실패 단계별 보드 |
| 교육 진행 | `/trainings` | 진행 이력 목록, 연도·상태 필터, 매출·수료 인원 집계 |
| 교육 과정 | `/courses` | 자사 과정 마스터와 과정별 운영 실적 |
| 활동 기록 | `/activities` | 전화·미팅·메일 로그, 미완료 후속조치만 보기 |

## 정례화된 관리가 돌아가는 방식

이 시스템의 핵심은 "누구에게 언제 연락해야 하는가"를 감이 아니라 규칙으로 뽑아내는 것입니다.

```
        등급 평가                프로파일                생애주기
   (구매빈도·반복성·재교육      (예산월·채용시즌       (거래 이력에서
    ·솔루션·상징성)             ·교육시즌)             자동 계산)
          │                        │                      │
          ▼                        ▼                      ▼
     접촉 주기 결정            시즌 이벤트            관계 점검 대상
    (S 2주 … D 24주)         (그 달에 챙길 곳)      (이탈위험·휴면)
          │                        │                      │
          └────────────┬───────────┴──────────────────────┘
                       ▼
                 컨택 아젠다 (/agenda)
              주간: 지금 연락할 곳 + 후속 조치
              월간: 이번 달 제안 타이밍
```

### 등급 산정

5개 축을 각각 1~5점으로 평가하고 가중 평균을 냅니다. 가중치와 등급 구간은
`src/lib/grade.ts` 한 곳에만 있으므로 운영하면서 조정할 수 있습니다.

| 축 | 가중치 | 보는 것 |
|---|---|---|
| 실제 구매 빈도 | 30% | 실제로 발주가 나오는가 |
| 반복 교육 가능성 | 25% | 정기 과정으로 자리잡을 수 있는가 |
| 재교육 가능성 | 15% | 같은 과정을 다른 차수로 다시 열 수 있는가 |
| 솔루션 제안 가능성 | 15% | 과정 납품을 넘어 체계 구축을 제안할 수 있는가 |
| 신뢰도·대외 상징성 | 15% | 레퍼런스로 내세울 수 있는가 |

가중 평균 4.3 이상 S / 3.6 이상 A / 2.8 이상 B / 2.0 이상 C / 그 미만 D.

- 각 축의 1~5점이 무슨 뜻인지 평가 화면에 문장으로 붙어 있습니다. "3점"의 해석이
  사람마다 다르면 등급이 의미를 잃기 때문입니다.
- "실제 구매 빈도"는 완료 교육 이력에서 **참고값을 자동 제안**합니다.
- 아직 판단이 안 서는 축은 비워 둘 수 있고, 평가한 축들만으로 평균을 냅니다.
- 계산 결과가 현장 감각과 다르면 **등급을 직접 지정**할 수 있습니다.
- 등급이 정해지면 접촉 주기가 따라옵니다: **S 2주 / A 4주 / B 8주 / C 12주 / D 24주**
  (고객사별로 직접 지정 가능)

### 생애주기

입력하는 값이 아니라 거래 이력에서 **자동으로 계산**합니다. 입력을 요구하면
반드시 낡은 값이 남기 때문입니다.

| 단계 | 판정 기준 |
|---|---|
| 발굴 | 완료 거래 0건 |
| 첫거래 | 1건 |
| 반복거래 | 2건 이상 |
| 확장 | 3건 이상이고 서로 다른 분류의 과정 2개 이상 |
| 이탈위험 | 마지막 거래 후 12개월 경과 |
| 휴면 | 마지막 거래 후 18개월 경과 |

### 프로파일 완성도

통화에서 파악해야 할 12개 항목 중 몇 개를 알고 있는지 백분율로 보여 주고,
**비어 있는 항목은 그대로 다음 통화의 질문 목록**이 됩니다.

> 예산 편성월이 비어 있으면 → "다음 해 교육 예산은 보통 몇 월에 편성하시나요?"

채워 넣은 예산월·채용 시즌·교육 시즌은 곧바로 월간 아젠다에 반영됩니다.

### 명함 이력과 담당자 교체

- **명함은 시점별로 쌓입니다.** 승진·부서이동·이직이 그대로 기록되고,
  직함이 바뀌면 `과장 → 차장 → 팀장` 형태의 변동 이력이 자동으로 만들어집니다.
- 가장 최근 명함을 등록하면 담당자의 현재 연락처도 함께 갱신되므로
  같은 값을 두 번 입력하지 않습니다.
- **담당자 교체는 별도 입력이 없습니다.** 담당자의 재직 상태를 '퇴사' 등으로 바꾸고
  후임을 지정하면, 고객사 화면의 "담당자 변경 이력"이 자동으로 만들어집니다.
  현재 창구(재직)와 지나간 담당자가 화면에서 분리됩니다.

## 데이터 모델

```
Organization (고객사)
├── AccountProfile (기업 프로파일)  1:1 — 예산·시즌·HR구조·확장 가능성
├── Contact        (담당자)         기관당 여러 명, 대표 담당자 1명
│   └── BusinessCard (명함 이력)    시점별로 여러 장
├── Training       (교육 진행)      ─── Course (교육 과정 마스터)
├── Deal           (영업 기회)      단계·예상 매출·성사 확률
└── Activity       (활동 기록)      담당자·영업건과 선택적으로 연결, 후속 조치 포함
```

- **Organization** — 기관명, 사업자등록번호, 기관 유형(기업/공공기관/지자체/대학/병원/비영리),
  업종, 규모, 임직원 수, 거래 상태(잠재고객/거래중/휴면/종료), 사내 영업 담당자,
  유입 경로·최초 접촉일, 등급 평가 5개 축, 접촉 주기
- **AccountProfile** — 인력 구성(내근/현장), HR 조직 구조, 의사결정 구조, 회계연도·예산 편성월·
  예산 규모, 채용 시즌, 교육 시즌, 정기 교육, 조직문화 활동, 기존 거래 업체, 타 부서 확장 가능성
- **Contact** — 부서·직급·연락처, 첫 만남(날짜/경로/장소/소개자), 재직 상태, 담당 기간,
  변경 사유, 후임 담당자, 인계 내용
- **BusinessCard** — 받은 날짜와 그 시점의 소속·부서·직함·연락처, 받은 경로·장소, 이미지 링크
- **Course** — 과정코드, 분류(리더십/직무/법정의무/DX·AI/CS/조직문화), 형태(집합/온라인/블렌디드),
  시수, 1인당 기본 단가, 최소 개설 인원
- **Training** — 차수명, 기간, 인원, 단가, 총 계약금액, 장소, 강사, 상태, 만족도
- **Deal** — 단계, 예상 매출, 성사 확률, 예상 마감일, 실패 사유
- **Activity** — 유형, 일자, 요약·상세, 후속 조치와 기한, 완료 여부

선택 목록(기관 유형, 영업 단계 등)은 DB enum 이 아니라 `src/lib/constants.ts` 의
문자열 배열로 관리합니다. 항목을 추가·변경할 때 마이그레이션이 필요 없고,
나중에 PostgreSQL 로 옮길 때도 그대로 동작합니다.

## 알아두면 좋은 동작

- **총 계약금액 자동 계산** — 교육 등록 시 총액을 비워 두면 `인원 × 단가`로 채웁니다.
  협의로 금액이 달라지면 직접 입력한 값이 우선합니다.
- **성사 확률 자동 설정** — 영업건의 확률을 비워 두면 단계별 기본값(문의 10% … 계약 90%)이
  들어갑니다. 파이프라인 보드의 좌/우 버튼으로 단계를 옮기면 확률도 함께 갱신됩니다.
- **가중 예상 매출** — 파이프라인 요약의 "가중"은 `예상 매출 × 성사 확률`의 합입니다.
- **대표 담당자** — 한 고객사에 대표를 새로 지정하면 기존 대표는 자동으로 해제됩니다.
- **고객사 삭제** — 담당자·교육 이력·영업건·활동 기록이 함께 삭제됩니다.
  과정을 삭제할 때는 교육 이력이 지워지지 않고 과정 연결만 해제됩니다.
- **누적 매출** 집계는 상태가 `완료`인 교육만 셉니다. 예정·진행중은 제외됩니다.
- **파이프라인 보드**는 드래그 대신 버튼으로 단계를 옮깁니다. 자바스크립트가 꺼져 있어도 동작합니다.

## 기술 스택

- **Next.js 15** (App Router, Server Actions) — 별도 API 서버 없이 서버에서 직접 DB 접근
- **Prisma 6 + SQLite** — 파일 하나로 시작. 운영 규모가 커지면 PostgreSQL 로 전환
- **Tailwind CSS 4** — 라이트/다크 모드는 시스템 설정을 따름
- **TypeScript**

## PostgreSQL 로 전환하기

동시 사용자가 늘거나 여러 서버에서 붙어야 하면 SQLite 로는 한계가 있습니다.

1. `prisma/schema.prisma` 의 `datasource db { provider = "sqlite" }` 를 `"postgresql"` 로 변경
2. `.env` 의 `DATABASE_URL` 을 PostgreSQL 접속 문자열로 변경
3. `npx prisma db push` 실행

스키마에 SQLite 전용 기능을 쓰지 않았기 때문에 코드 수정은 필요 없습니다.
다만 `src/app/organizations/page.tsx` 등의 검색은 SQLite 에 맞춰 `contains` 만 쓰고 있으므로,
PostgreSQL 에서는 `mode: "insensitive"` 를 추가하면 영문 대소문자 구분 없는 검색이 됩니다.

## 아직 없는 것

지금은 로그인이 없어 접근하는 모든 사람이 전체 데이터를 보고 수정할 수 있습니다.
사내망 밖에 두거나 여러 담당자가 나눠 쓸 계획이라면 다음이 필요합니다.

- 사용자 인증과 권한 (담당 고객사만 보기 등)
- 변경 이력 로그
- 엑셀 가져오기/내보내기
- 첨부파일(제안서, 계약서) 보관
